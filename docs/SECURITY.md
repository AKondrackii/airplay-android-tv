# Безопасность

## Модель угроз
Приёмник слушает TCP-порт (по умолчанию 7000) и UDP-порты RTP в локальной сети. Угрозы:
посторонние устройства в той же сети или в гостевой сети, хосты из других подсетей и интернета,
локальные приложения на самом ТВ, некорректные и специально сформированные пакеты, исчерпание ресурсов.

## Меры защиты

### 1. Только локальная сеть (всегда включено)
- Учитываются только сети **Wi-Fi и Ethernet** без VPN (`NetworkMonitor`). Мобильная сеть, VPN,
  Bluetooth-тетеринг и прочие сети игнорируются. Если подходящей сети нет, приёмник останавливается.
- mDNS-анонс привязан к IP **одного** разрешённого интерфейса, поэтому в других сетях приёмник не виден.
- **Каждое TCP-соединение** проверяется сразу после `accept()`, до разбора хотя бы одного байта (`SubnetFilter`):
  - локальный адрес соединения должен быть адресом разрешённого интерфейса (так отсекаются VPN и вторые сетевые карты);
  - адрес клиента должен попадать в **подсеть этого интерфейса по реальной маске**, а не просто в «частный диапазон»;
  - сетевой, широковещательный, multicast-адреса, `0.0.0.0` и адрес самого ТВ отклоняются;
  - слишком широкие префиксы (IPv4 короче /8, IPv6 короче /48) локальной сетью не считаются;
  - loopback разрешён **только во время AirPlay-видео** (нужен локальному HLS-прокси). В остальное время
    приложения на самом ТВ подключиться не могут.
- При смене сети (переподключение Wi-Fi, новый IP) разрешённые подсети пересчитываются, а приёмник
  и анонс перезапускаются (`ReceiverController`).
- Облака, relay-серверов, телеметрии и удалённого доступа нет. UPnP/NAT-PMP не используются.

**Гостевая сеть.** Обычно у гостевого SSID своя подсеть, и её клиенты отклоняются по маске. Если
роутер выдаёт гостям адреса из основной подсети, отличить их по IP невозможно. Для такого случая
есть PIN и подтверждение подключений.

### 2. Аутентификация (проверяется протоколом, а не только интерфейсом)
| Режим | Механизм | Где проверяется |
|---|---|---|
| PIN на экране | Legacy-сопряжение AirPlay: SRP-6a с 4-значным PIN, затем Ed25519-ключ клиента сохраняется | `pairing.c`/`srp.c` (UxPlay), `check_register` → `TrustedDeviceStore` |
| Постоянный пароль | HTTP Digest в RTSP (`WWW-Authenticate`, ответ 401) | `raop_handlers.h` (UxPlay) |
| Одноразовый код | HTTP Digest со случайным 4-значным кодом на каждое подключение; после 3 неудачных попыток код меняется | `raop_handlers.h` (UxPlay) |
| Подтверждение новых устройств | Запрос RTSP SETUP блокируется до ответа пользователя (25 с, затем отказ) | `ReceiverPolicy.admitClient` |

- **Доверенные устройства.** Если устройство прошло PIN-сопряжение, его ключ проверяется криптографически
  при каждом `pair-verify`. Если устройство просто подтвердили на экране, оно опознаётся по `deviceID`,
  который протокол **не аутентифицирует**. UI показывает эту разницу честно.
- После отказа устройство автоматически отклоняется ещё 60 секунд, чтобы запросы не спамили экран.
  Одновременно ожидает ответа только один запрос.
- Удаление доверенного устройства сразу отзывает доступ: при следующем `pair-verify` ключ не будет найден.

### 3. Ресурсы и некорректный ввод
- Rate limiting: не больше 24 TCP-соединений с одного адреса за 10 секунд, иначе блокировка на 60 секунд.
  Таблица хостов ограничена (LRU).
- Не больше 12 одновременных соединений (`MAX_CONNECTIONS` в httpd UxPlay). Пока идёт сессия, другие клиенты получают 409 «занято» и не могут её прервать.
- Заголовки ограничены: до 20 полей, имя до 64 байт, значение до 1024 байт (UxPlay).
- Строки из сети (имена устройств) перед передачей в JVM проверяются как UTF-8 и обрезаются.
  Метаданные ограничены 64 КБ, обложки — 4 МБ, кадр видео — 8 МБ.
- `assert` в коде UxPlay **остаются включёнными в release**: нарушение инварианта приводит к контролируемому
  падению и перезапуску сервиса, а не к неопределённому поведению.
- Найдено фаззингом и исправлено (патчи помечены `AIRPLAYTV:`):
  1. NULL-колбэк `audio_set_client_volume` при запросе `/info`: SIGSEGV с одного пакета;
  2. запрос без версии протокола приводил к `assert(datalen > 0)`: abort с одного пакета;
  3. ответ 431 на длинные заголовки отправлялся незавершённым: `assert(response->complete)`, abort;
  4. чужой или отсутствующий `X-Apple-Session-ID`: `strcmp` по NULL или assert;
  5. `/pair-pin-start` выводил PIN на экран ТВ даже при выключенной защите.

### 4. Хранение секретов
- Пароль, Ed25519-ключ приёмника, ID устройства и список доверенных устройств хранятся зашифрованными
  AES-256-GCM. Ключ находится в **Android Keystore** и не покидает его (`SecretStore`).
- UxPlay читает ключ из PEM-файла. Расшифрованная копия существует только на время инициализации
  в `noBackupFilesDir` приложения (недоступна другим приложениям), затем она затирается и удаляется.
- Резервное копирование отключено (`allowBackup=false`, правила извлечения данных пустые).
- Собственной криптографии нет: используются OpenSSL 3.5 LTS и платформенный AES-GCM.

### 5. Приватность
Аналитики, телеметрии и отчётов о сбоях нет. Единственный исходящий запрос самого приложения — проверка
обновлений (`GET https://api.github.com/repos/<repo>/releases/latest` раз в 12 часов, отключается в настройках);
кроме стандартных HTTP-заголовков, ничего не передаётся. Загруженный APK устанавливается, только если совпали
SHA-256 из `SHA256SUMS.txt` релиза, имя пакета, версия и сертификат подписи; установку всегда подтверждает
пользователь в системном окне Android, а APK с чужой подписью Android не установит поверх приложения. Видео и звук не записываются. История подключений
не ведётся, журнал ошибок живёт только в памяти. Обложки и метаданные существуют только в памяти,
пока идёт воспроизведение. Приложение само не обращается ни к каким серверам. Исключение — AirPlay-видео:
в этом режиме ТВ загружает поток по ссылке, которую передал iPhone, так же как Apple TV.

## Известные ограничения
- RTP/UDP-порты аудио и NTP, а также TCP-порт видеоданных повтора экрана не проходят через фильтр httpd. Пакеты без ключа сессии, полученного
  по защищённому TCP-каналу, расшифровать и применить нельзя.
- Шифрование потока определяется протоколом AirPlay (AES-CTR/CBC); его стойкость к активному
  атакующему в той же сети ограничена дизайном Apple.
